# The same columns can enclose a square

Audited 3 November 2026. This follows the [initial measuring bench review](count-measure-review.md), whose unpushed status and receipts describe that earlier stage.

The concrete question is whether a column count determines a temple's proportions. Hold a trial at equal 3 D pitches, then choose **Use half the front pitch**. The blue trial becomes a 15 × 15 D centre square while the red reference remains 15 × 30 D. Both retain the same 30 physical columns. This is a modern counterexample to inferring distances from counts alone; it does not settle what Vitruvius intended by *longitudo operis*.

## Reproduced defects and resulting behavior

| Trigger | Earlier behavior | Reviewed behavior |
| --- | --- | --- |
| Choose 6 D front and flank pitches, then halve | Front silently reset to 3 D | Front stays 6 D; flank becomes 3 D |
| Halve 2.55 D | A copied link rounded 1.275 D | Exact admitted half pitch survives link and work-file reopening |
| Unlock equal pitches without moving them | Explanation claimed pitches differed | Explanation follows actual values |
| Compare two spacing choices | Previous drawing and its count source disappeared | Hold a red reference; both drawings, rulers and sources survive native exports |
| Read a source actively arriving beyond 15 seconds | Healthy source aborted | Chunk progress resets an inactivity clock; complete bytes are hashed before use |
| Reload a damaged source taking over a minute through a controlling worker | Page failed while data was still arriving, including a Firefox failure around 61 seconds | Designated verified reader fetches directly, hashes bytes, then offers them to the worker for an independent check |
| Cancel a Plans illustrated reading | UI cancelled, network signal remained live | Cancellation aborts all pending source and font reads |

The half-pitch button is unavailable below a 2.5 D front pitch, with a visible explanation of the 1.25 D minimum. It never moves another control to conceal the limit. Equal-spacing preset and restoration remain explicit separate actions.

## Transfer and offline behavior

One typed transfer helper is compiled into the page modules and generated worker. It permits 60 seconds for headers, 15 seconds without a nonempty body chunk, at most 180 seconds total and at most 32 MiB per asset. Reading aggregates allow 195 seconds and abort their sibling reads on failure or cancellation. These are bounded application policies, not network-speed promises.

The direct verified-source route avoids a worker-owned response stream. This resolved the observed long-transfer browser failures; the review does not identify an engine-internal cause. The page checks its expected hash before display/export. Its cache offer is independently checked by the current worker against the build's own edition, source client scope, known source/font/notice path, size and SHA-256. A false offer cannot replace saved bytes. A valid source offer cannot declare the entire edition ready. Readiness still requires the current controller and inspection of every retained file.

The full cold-install audit also reproduced Firefox abandoning an initial installation after about a minute, with 61 of its 88 retained assets saved. Initial installation can now resume automatically only while the current edition's saved-file count increases, the browser reports online, and fewer than eight resume attempts have occurred. The count is a scheduling hint, never a readiness test: each saved file is independently hashed again by the installer. Repeated failure without progress exposes **Retry offline saving**; that control continues without discarding the learner's current work or requiring a reload.

A failed explicit reload may use the current edition's saved copy only after hashing it again. A missing copy starts no second network wait. Failed repair leaves previous bytes unchanged. Buffered decoded responses remove origin compression headers and describe the decoded body length.
